## 未通過項目

「實測」是 harness 當下量到的原始訊息,與終端機輸出逐字相同,故保留原文;「為什麼重要」是這條需求的中文說明。

### CFG-03 — 過長的 poll plan 應被拒絕,而不是被截斷

實測:an over-sized plan returned applied — the last polls would be dropped from every uplink with nothing to say so

為什麼重要:8 個 poll × 16 個暫存器等於 272 bytes,但一個封包只裝得下 233;引擎會把後面的 poll 整個丟掉,那些點位就永遠沒有資料,而且沒有任何地方會告訴你。

### CFG-07 — 縮短回報間隔後應立即生效

實測:the next poll came 21.9s after the change, not ~4s — the node sat out the old 25s interval first. A unit moved from hourly to minutely reporting stays silent for up to an hour and reads as dead

為什麼重要:applyConfigBlob() 會重新初始化 UART,卻從來沒有重排輪詢執行緒的排程,所以剛回傳過 uplink_interval_s * 1000 的節點會先把「舊的」間隔睡完。把一台單位從每小時改成每分鐘回報,它會有長達一小時看起來像故障。

### POLL-07 — 從機拒絕時回報為 exception,而不是 timeout

實測:errors were ['timeout', 'timeout'], expected 'exception' — a wrong register in the plan would look like an unplugged cable

為什麼重要:否則 plan 裡寫錯一個暫存器,看起來會跟線沒接完全一樣,技術人員會被派到現場錯誤的那一端。

### POLL-08 — 從機自己的 exception code 有帶進 payload

實測:exception codes were [None, None], expected 0x02

為什麼重要:「illegal data address」和「device busy」需要完全相反的處理;沒有那個碼,技術人員無從分辨該修 plan 還是該檢查裝置。

### POLL-09 — 永久性的拒絕不應該被重試

實測:refusal took 8091 ms — retries are still being spent on it

為什麼重要:再問三次某個暫存器存不存在也不會改變答案,只是白白花掉匯流排時間與電池。
